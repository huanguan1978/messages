# AI 多语言翻译作业指引

> 适用场景：项目已完全接入 `basic_message`（消息已定义、译文文件的自动生成流程已打通、程序可按语言切换显示文案），要把全部消息的**真实翻译**交给 AI 完成。
> 阅读对象：第一次做这项工作的开发者（个人/小团队），及执行翻译作业的 AI 会话。
> 指引可及性：本文件随包分发，path 依赖时 AI 可直接读包内 `doc/zh/`；其他引入方式（pub 缓存等）请先复制进项目（如 `doc/`）再在会话中引用。
> 生词见 1.1；配套工具见第六节；本文引用的 SKILL 指 `skills/basic-message-l10n/SKILL.md`。

---

## 一、为什么不能"直接把 arb 文件丢给 AI 翻"

| 问题 | 解法（详见） |
|---|---|
| AI 不知道每条文案在哪里出现、什么场景触发，同词多义全靠猜 | 翻译上下文包：真实调用点源码快照（第六节） |
| 调用点上下文被 `dart format` 折行切碎，按行截取只剩残片 | 按 AST 节点提取，对折行免疫（6.1） |
| 术语翻法漂移（Preset 一会儿"预设"一会儿"方案"） | 全局词表，人工拍板后全批强制对齐（3.3） |
| 几百上千条消息逐条人工校对，个人开发者做不完、质量也没法保证 | 只上报 AI **自己没把握**的条目，且做成选择题（3.2） |
| 键名前缀、目录名与实际语义对不上（命名规范非强约束） | 由 AI 做语义统筹，键名/路径只作旁证（3.2） |
| 译文破坏 ICU 结构（占位符改名、select 分支丢失） | 机检闭环 + 红线 2/3（3.5、第四节） |
| 全量周期长，中途管线不能停 | 缺译条目程序自动回退显示英文，可分批、可暂停（3.1） |

**分工原则：确定性环节交给工具和管线，理解性环节交给 AI，产品级决策留给开发者拍板。**

### 1.1 名词释义

| 名词 | 通俗解释 |
|---|---|
| 消息 | 界面文案在代码里的登记条目，每条有唯一编号和键名 |
| arb 文件 | 存放全部消息原文与译文的 JSON 文件；`intl_en.arb` 为英文底稿，`intl_zh.arb` 等为译文文件 |
| 基准 arb | 即 `intl_en.arb`，一切翻译的对照底稿 |
| 生成管线 | 一串自动命令：定义→英文底稿→程序用的代码；译文改完要重跑才生效 |
| 运行时接入 | 程序运行时按当前语言取到译文的能力（已接入项目无需关心细节） |
| 占位符 | 文案里预留的空位，如 `{name}`，显示时填入真实值 |
| ICU 表达式 | 处理复数、枚举选择的特殊语法（`plural`/`select`），结构有严格规则（红线 2/3） |
| 翻译上下文包 | 配套工具产出的 JSON 材料包：每条消息附它在源代码里的真实使用现场 |
| 置信度 | AI 的把握程度。高：直接定稿；中：自行判断并记录理由备查；低：必须做成选择题交人定夺 |
| 语义统筹 | AI 通读全部材料后的全局归类：每条消息属于哪块业务（domain）、哪个生命周期层级（st/cd/rs） |
| 词表 | 全局术语对照表和行文规则，保证全部文案用词一致 |
| 机检 | 每批结束后的自动检查：译文结构完整、生成管线能跑通 |

## 二、流程总览

```
① 复制基线    intl_en.arb → intl_zh.arb（补 @@locale，值暂保持英文）
② 语义统筹    AI 产出 translation_plan.json → 开发者拍板
③ 全局词表    AI 提炼 glossary_zh.json → 开发者拍板
④ 逐批翻译    外层 st→cd→rs，层内按 domain；每批跑机检；决策回流词表
⑤ 机检闭环    结构校验 → 管线复跑 → analyze → 台账（AI 自查 + 工具执行）

全部批次完成后按第八节验收。
```

## 三、协议细则

### 3.1 ① 复制基线

- 复制 `intl_en.arb` 为目标语言文件，根元数据补 `@@locale`（简体 `zh`，繁体 `zh_Hant` / `zh_Hant_HK`，避免歧义简写），**所有值暂保持英文原文**；
- 目的：生成管线任何时刻都能通过；程序遇到未译条目自动显示英文兜底——翻译因此可分批推进、随时暂停。

### 3.2 ② 语义统筹

AI 通读翻译上下文包（6.2 生成）的全部材料，为每条消息判定三个字段，落盘 `translation_plan.json`：

```json
{
  "code": 20126,
  "member": "stFbGlobalTitleParametersInspect",
  "msg": "Parameters: {id}{modified}",
  "domain": "preset_params",
  "lifecycle": "st",
  "evidence": "callSites: gen_content_page.dart _onMenuAction（inspect 弹窗标题）",
  "batch": "st-01"
}
```

| 字段 | 含义 | 判定依据（按参考价值排序） |
|---|---|---|
| `domain` | 语义域：属于哪块业务（如 `ai_chat`、`account_auth`、`task_scheduling`、`file_resource`、`app_generic`） | msg 内容 > 调用点上下文/owner 方法名 > 键名前缀、目录路径 |
| `lifecycle` | `st` 静态展示 / `cd` 校验守卫 / `rs` 执行反馈 | msg 功能形态与调用点形态（`title:` 参数→st；`catch` 块内→rs）；键名前缀仅作旁证。完整定义见 `doc/zh/L10N_NAMING_GUIDE2.md` |
| `evidence` | 划分依据摘要 | 供拍板时快速核对 |

**零调用点条目（`callSites: []`）默认跳过**：来源于 `-i` 消息定义文件、但在 `-s` 源码范围中未检出直接调用点的条目，**默认无需处理并跳过翻译**（在 `translation_plan.json` 中标记为 `"status": "skipped"`，目标 ARB 保留英文原文），也不必逐条发问；仅当开发者在分组审批时显式指定其中确属间接消费（如经错误码 formatter 或枚举映射分发）的条目，才纳入翻译。

**低置信项处理（人工接口）**：低置信项 = AI 没把握、需人定夺的条目，**不得硬判**——整理成选择题上报：每题附证据摘要、2-3 个选项、推荐项；开发者只挑选项、不打字描述（开放式反馈容易偏离本意）。迭代至全部消解后，开发者对 `translation_plan.json` 整体拍板。

**上报量预算（硬规则）**：选择题不得超过消息总量的约 10%；超出时 AI 必须自行决断并记录理由，不得把问题倾倒给开发者。

### 3.3 ③ 全局词表

AI 基于统筹定稿的语义分组提炼 `glossary_zh.json`：

- **术语定译**：高频域名词（Preset→预设、MCP Configuration→MCP 配置、Scheduled Task→定时任务…）；
- **不译项**：保留英文的技术词（MCP、API、ID、URL…）——技术标识与用户文案的边界判定见 `doc/zh/L10N_STRATEGY_GUIDE.md`；
- **语气规则**：全局选择（zh 用"你"还是"您"、按钮用"确定"还是"好"…）。

拍板后对全部批次强制生效；**词表是产品级决策，AI 不得擅自变更**。批内存疑决策可回流补充，但词表变更只发生在批边界，已完成批次不受扰动。

### 3.4 ④ 逐批翻译

**排序：外层按生命周期 `st → cd → rs`，层内按 `domain` 分批。** 依据有三：

1. **依赖方向**：cd/rs 的参数值大量引用 st 标签消息（`{type}` 传 select 标签、`{item}` 传 ID 标签等），先翻 st 等于先定稿所有"被引用的参数值文案"，避免返工；
2. **难度梯度**：st 短句 → cd 带条件参数 → rs 带复数/select 与语气细节；
3. **协议试运行**：首批顺带验证作业链路（本指引、上报格式、机检），成本最低的批承担试错。

**每批规则：**

1. 先读词表，术语严格对齐；
2. 先凭 msg + desc + 参数示例直译；**拿不准才读上下文包的调用点快照**——不是每条都翻源码，这是成本控制关键；
3. 三级判定：直接译 / 查现场推导 / 标低置信上报（宁缺毋滥，不硬猜）；
4. 低置信项攒批一次性上报，提供"全部采纳推荐项"快捷路径；
5. 被回答的选择题立即沉淀为词表条目，后续批次同场景不再重复提问。

### 3.5 ⑤ 机检闭环（每批收尾）

1. **结构校验**（AI 自查）：逐条比对 en 与译文——占位符集合一致、select 的 case 键一致（只译分支值）、plural 类别一致；
2. **管线复跑**：按项目自己配置的生成命令，依次重跑"译文文件 → 本地化代码"步骤与 `gen_msg_registry`（标准命令与顺序见 6.5，权威说明见 SKILL 的 Workflow 第 9–11 步）；
3. **静态检查**：`flutter analyze` / `dart analyze`；
4. **进度台账**：生成时列出的"未翻译条目清单"即剩余工作量；批进度记入 `translation_plan.json`。

### 3.6 会话怎么开（可复制模板）与文件布局

**文件布局**（均放项目内）：

| 文件 | 产生于 | 作用 |
|---|---|---|
| `lib/l10n/intl_en.arb` | 生成管线 | 英文基准（只读，改它=改需求） |
| `lib/l10n/intl_zh.arb` 等 | ① 复制、④ 逐批写入 | 译文文件（唯一最终产物） |
| `lib/l10n/messages_analyzer.g.json` | 配套工具现算 | 翻译上下文包（临时材料，可随时重生成） |
| `lib/l10n/translation_plan.json` | ② 统筹 | 分组/顺序/进度台账（拍板后只读，批进度除外） |
| `lib/l10n/glossary_zh.json` | ③ 词表 | 术语与行文规则（拍板后只读，批边界回流） |
| 低置信上报、中置信日志 | ②④ | 会话内呈现，决策结果回写上面两份文件 |

**② 语义统筹（一次性会话）：**

```text
请按 doc/zh/AI_TRANSLATION_GUIDE.md 3.2 的协议执行语义统筹：
1. 先运行 6.2 的 gen_msg_analyzer 命令生成翻译上下文包（若尚无）；
2. 通读 lib/l10n/messages_analyzer.g.json 全量材料，
   产出 lib/l10n/translation_plan.json（domain / lifecycle / evidence / batch）；
3. 低置信项按 3.2 的选择题格式上报（附推荐项与证据），迭代至全部消解；
4. 完成后交我整体拍板，拍板前不要开始任何翻译。
```

**③ 全局词表（一次性会话）：**

```text
请按 doc/zh/AI_TRANSLATION_GUIDE.md 3.3 的协议提炼全局词表：
基于 lib/l10n/translation_plan.json 的语义分组，
产出 lib/l10n/glossary_zh.json（术语定译 / 不译项 / 语气规则）；
低置信术语同样以选择题上报，交我拍板。
```

**④ 逐批翻译（每批一次会话，按批号填空）：**

```text
请按 doc/zh/AI_TRANSLATION_GUIDE.md 的协议执行第 <N> 批翻译：
1. 读 lib/l10n/translation_plan.json 中 batch = "<N>" 的条目；
2. 读 lib/l10n/glossary_zh.json，术语严格对齐；
3. 按 3.4 的作业规则翻译，写入 lib/l10n/intl_zh.arb；
4. 低置信项按 3.2 的选择题格式上报（附推荐项与证据），不要硬猜；
5. 完成后执行 3.5 的机检闭环并汇报结果与剩余工作量。
```

**会话中断怎么续**：重发模板、换下一个未完成批号即可；`translation_plan.json` 的批进度 + arb 已译条目就是断点状态，不依赖会话记忆。

## 四、协议约束（红线）

任何一条不满足即视为该批未完成：

1. **占位符原样保留**：`{xx}` 的名字、数量、位置不得改动；
2. **ICU 表达式独占整条消息**：原文是纯 `select`/`plural`，译文也必须是纯表达式，**首尾不得加任何文字**——`intl_translation` 0.21.0 的解析器只在整个消息以 ICU 表达式开头时才走 ICU 路径，混排会报 `Cannot find parameter named 'XXX'`（权威出处：SKILL 的 **ICU Expression Isolation** 条目；基础语法示例见 `doc/zh/L10N_DESIGN_GUIDE.md`）；
3. **select/plural 必须保留 `other` 分支**，case 键名不得翻译；
4. **术语对齐词表**，不得临场发明译法；
5. **宁缺毋滥**：无法消解的低置信条目保持英文原文并标记待定，不得硬猜；
6. **上报量 ≤10%**，超出必须自行决断并记录理由；
7. **不手改生成文件**：`*.g.dart` 一律由管线产出；
8. **机检通过 ≠ 语义正确**：每批完成后仍需小比例人读抽查，发现的问题按 3.4 低置信流程回流。

## 五、常遇问题速查

| 症状 | 原因 | 处置 |
|---|---|---|
| `Cannot find parameter named 'XXX'` | select/plural 未独占整条消息（混入普通文本） | 拆成"纯 select/plural 标签消息 + plain 参数正文"两条 |
| 译文 select 分支丢失或 case 键被翻译 | AI 误改结构 | 机检第 1 步拦截；重翻该条（红线 3） |
| 中断续作后术语与之前不一致 | 词表未强制对齐或批间漂移 | 回读 `glossary_zh.json`；不一致批次复查 |
| 生成时提示有"未翻译条目" | 该批尚未翻到，属预期 | 程序回退显示英文；以清单为进度表 |
| 同一消息调用点分散在多个业务域 | 通用文案，属正常 | 归入 `app_generic`，最早批次翻译 |
| 工具报某消息零调用点 | `-i` 定义文件中的未使用/预留条目，或经公共入口间接消费（如错误码 formatter） | 默认跳过（在 `translation_plan.json` 标记为 `"skipped"` 并保留英文原文）；仅在开发者于分组审批时显式指定为间接消费条目时才翻译；死键可另行清理 |

## 六、配套工具：gen_msg_analyzer

### 6.1 用途与原理

为每条消息收集**真实调用点**上下文，产出翻译上下文包。上下文按 AST 节点提取三层——L1 调用表达式 / L2 语句或 catch 子句 / L3 所属方法与类名——`dart format` 只改空白不改语法结构，故**对折行免疫**。

### 6.2 用法

```bash
dart run basic_message:gen_msg_analyzer \
  -i lib/message/definition.dart \
  -s . \
  -o lib/l10n/messages_analyzer.g.json
```

| 参数 | 说明 |
|---|---|
| `-i, --input` | 消息定义文件（MessageEnum 所在文件） |
| `-s, --source` | 项目根目录（扫描调用点的范围） |
| `-o, --output` | 输出 JSON（建议 `lib/l10n/`，与 arb 同目录） |
| `-m, --max-snippet` | 单条快照最大字符数，默认 2000、**下限 2000**（低于自动抬升并提示）。超过语义单元长度后收益递减，2000 为经验平衡点 |

### 6.3 输出结构（每条消息）

```json
{
  "code": 20110,
  "key": "st_fb_action_failed",
  "member": "stFbGlobalSnackbarActionFailed",
  "msg": "{action} failed: {error}",
  "desc": "……",
  "paramExamples": { "action": "loadPreset", "error": "…" },
  "callSites": [
    {
      "file": "lib/page/publ/talking/chat_page.dart",
      "line": 222,
      "call": "ME.tr(MD.stFbGlobalSnackbarActionFailed, args: {'action': 'loadConversationHistory', 'error': '$e'})",
      "context": "AppGlobal.showSnackBar( ME.tr( … ) );",
      "owner": "_ChatPageState._loadHistory"
    }
  ]
}
```

| 字段 | 对翻译的价值 |
|---|---|
| `call` | 完整调用表达式（实参字面量常是语义线索） |
| `context` | 外层语义单元（`catch` 块、`if` 分支）——判断成功/失败场景的关键 |
| `owner` | 所属类与方法名——判断在什么功能里被调用 |
| `paramExamples` | 参数代表值——判断参数语义 |

嵌套调用（参数值本身是另一个 `ME.tr(...)`）会被完整捕获，不被折行截断。

### 6.4 行为说明

- 自动排除：隐藏目录、`.dart_tool`/`build`、`*.g.dart`、定义文件自身、输出文件自身；
- 文本预过滤（不含目标名的文件不解析），数百文件秒级完成；
- 结束时报告**零调用点消息清单**——死键探测器 + "经公共入口间接消费"提醒（见第五节末行）；
- 产物为**每次现算的临时材料**：不写进 arb、不持久化到定义，代码演进后重跑即可，永不腐烂。

### 6.5 basic_message 配套工具一览

| 工具 | 调用方式 | 在翻译流程中的位置 |
|---|---|---|
| `gen_msg_analyzer` | `dart run basic_message:gen_msg_analyzer` | **本指引核心**：翻译上下文包（②③④的材料来源） |
| `gen_msg_resource` | `dart run basic_message:gen_msg_resource` | 生成管线第一步：定义 → 资源文件（翻译前应已跑通；权威用法见 SKILL Workflow 第 9–11 步） |
| `gen_msg_registry` | `dart run basic_message:gen_msg_registry` | 生成管线末步：运行时注册表（机检 3.5 的一环） |
| `intl_translation` / `flutter gen-l10n` | 外部包 | ARB 提取与本地化代码生成（具体命令以项目自身脚本配置为准） |

## 七、注意事项

1. **基准稳定约束（全盘翻译的前提）**：整个流程假设基准 arb（`intl_en.arb`）已稳定不变。若基准随后变化：
   - **新增消息**：可做增量翻译——只译多出的部分；
   - **已有消息变更**：模型并不知道哪些已译条目受影响而需重译，增量**不包含**这部分——要么完整重译，要么明确指定重译范围；
   - 判断基准是否变过：对比 `intl_en.arb` 与上次翻译时版本（条数 + 逐条 diff）。
2. **材料新鲜度**：每次会话开工前重新生成上下文包；定义或调用点变更后，涉及批次重跑并复核；
3. **输出文件位置**：`-o` 指向的文件自动排除在扫描外，可放心放项目内；
4. **词表拍板不可跳过**：跳过词表是术语漂移的最主要根源；
5. **中置信日志**：AI 自动决断的理由写入 sidecar 日志（不进 arb），供事后抽查；
6. **多语言扩展**：先在一种语言（建议 zh）上把协议跑顺，其余语言（如 `zh_Hant_HK`）基于已完成语言派生，成本大幅降低；
7. **派生翻译同样过机检**：繁体等派生语言也会破坏 ICU 结构；
8. **与 SKILL 的分工**：本指引只覆盖翻译阶段；定义阶段规则（键名五级结构、号段、ICU 约束）以 SKILL 为准；
9. **版本敏感**：解析行为绑定 `intl_translation` 0.21.0；升级后如混排消息可正确解析，红线 2 需同步修订。

## 八、完成判定（一个语言何时算"翻完"）

全部批次完成后逐项核对，全部满足才可宣布完成：

- [ ] 生成时的"未翻译条目清单"为空；
- [ ] `translation_plan.json` 所有批次完成，无未清存疑/待定条目（仅按规则跳过的零调用点条目可保留英文原文，红线 5 遗留已全部消解）；
- [ ] 每批机检通过，且**收尾时完整重跑一遍生成管线与静态检查**（防跨批累积问题）；
- [ ] 翻译期间基准 arb 未变更；若变更过，已按第七节第 1 条完成重译或指定范围重译；
- [ ] 按红线 8 完成人读抽查并记录；发现的问题已全部回流修复。

验收通过后，`intl_<lang>.arb` 即为该语言正式译文；后续仅随消息定义演进做增量维护（第七节第 1 条）。
