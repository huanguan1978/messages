# L10N 分层本地化策略指南：骨架与负载分离（Skeleton vs. Payload）

> **核心主题：新手必须能用母语走主线，专家可以看英文调参数。**

## 1. 核心背景与现实困境

在软件界面设计与国际化（i18n / l10n）工程中，如果把“多语言化”理解成“必须同时翻译界面上的每一个字”，往往会遇到两个现实矛盾：

1. **用户完成任务所需的理解深度不同**
   - **新手 / 普通用户**：依赖默认配置和推荐路径完成操作，不需要先研究完整技术文档；
   - **熟手 / 高阶用户**：需要进入高级区域，精细调整领域参数，并可能对照技术规范或 API 文档进行操作。
2. **高级参数的变化速度和翻译成本较高**
   - 高级参数常随产品能力或底层协议变化而增删，过早全面翻译会增加持续维护成本；
   - 算法名、协议标识、数据格式和配置键通常已有国际通用名称，生硬直译反而可能损害准确性，也会让用户难以检索并对照原始文档。

因此，本地化不必从“逐字覆盖整个界面”开始，而应从“保障不同角色完成任务”开始：

> **先让新手能用母语完成推荐主线，再为专家调参决定哪些内容暂留原文、哪些内容需要翻译。**

本策略与 [L10N 命名与工作流规范](L10N_NAMING_GUIDE2.md) 分别解决两个不同的问题：前者决定“优先翻译什么”，后者规定“已纳入多语言资源的文本应如何组织”。两份文档并列使用，没有先后替代关系。

| 指引 | 主要回答的问题 | 负责范围 |
| :--- | :--- | :--- |
| 本策略指南 | 哪些内容应优先本地化？哪些技术名称可以保留原文？ | 角色分层、骨架与负载、翻译优先级 |
| 命名与工作流规范 | 已纳入多语言体系的消息怎样分类、命名和生成？ | `st` / `cd` / `rs`、五级语义坐标、消息生成流程 |

因此，先依据本策略判断文本是否需要纳入多语言资源；确定纳入后，再依据命名与工作流规范处理它。角色和骨架决定覆盖范围，生命周期分区决定消息命名。即使一段文本属于专家负载，只要它被正式纳入多语言资源，仍必须遵守命名与工作流规范。

---

## 2. 第一层：角色分层是主导原则

“角色”指用户在当前任务中的使用深度，并不是对用户身份的永久标签。同一个人可能在默认操作时属于新手，在进入调参区域时则属于专家。

### 2.1 新手 / 普通用户

为支持新手角色，界面至少应满足：

- 不依赖英文就能理解当前页面和所在区域；
- 不查阅外部技术文档也能使用推荐选项和默认配置；
- 能理解主要操作、任务状态和结果反馈；
- 遇到普通错误时能知道如何返回、重试或恢复。

所以，新手路径必须形成完整的母语闭环：

```text
进入页面 → 理解当前位置 → 使用推荐设置 → 执行操作 → 理解结果 → 必要时重试或返回
```

### 2.2 熟手 / 高阶用户

专家角色的目标是准确调参，并不要求把每个技术原文都先转换成母语。专家区域可以：

- 保留已有共识的行业英文术语；
- 保留协议名、算法名、API 参数名、配置键和枚举值；
- 使用母语解释导航、操作、风险和恢复方式；
- 提供与官方文档一致、可复制和可搜索的原始名称。

角色分层的主旨是：

> **新手必须能用母语走主线，专家可以看英文调参数。**

这里的“角色分层”决定产品界面的本地化优先级，不改变 `L10N_NAMING_GUIDE2.md` 中 `st`、`cd`、`rs` 的判定方法。新手主线内仍可能同时包含静态文案、条件校验和执行结果；它们仍应按实际出现阶段分类。

## 3. 第二层：先理解骨架与负载

要落实角色分层，首先要理解界面的两类职责：骨架提供寻路和操作控制能力，负载承载具体的业务与技术内容。

```text
              【骨架层：必须本地化】
       页面标题、导航、Tab、按钮、状态和反馈
                         │
                         ▼
┌────────────────────────────────────────────────────┐
│ 任务工作台                                           │
│ [ 基础设置 ]        [ 高级参数 ]   ← Tab 门牌          │
│────────────────────────────────────────────────────│
│  Temperature: 0.7                                  │
│  Top-P: 0.95                    ← 负载层            │
│  Local Files: Sandbox / Base64                     │
│────────────────────────────────────────────────────│
│ [ 恢复默认 ]                         [ 执行 ]        │
└────────────────────────────────────────────────────┘
```

### 3.1 骨架层（Skeleton）必须本地化

骨架层是界面的寻路和控制系统，决定用户能否知道“我在哪里”“现在能做什么”“接下来会发生什么”。

骨架至少包括：

- 页面标题和全局导航；
- Tab、抽屉、折叠面板和对话框标题；
- 提交、保存、执行、重置、返回等操作按钮；
- 进度、成功、失败等状态反馈；
- 影响用户继续操作的错误和恢复入口。

即使高级区域的内部内容暂留英文，其标题仍是新手识别区域用途的“门牌”。例如，用户只看到 `高级参数`，即使暂时不进入，也知道这里属于需要额外判断的非主线路径。规划好的英文区域不是随机漏译，它通过母语门牌预先建立了清晰边界。

### 3.2 负载层（Payload）可以按阶段处理

负载层是骨架内部具体承载的业务或技术内容，例如：

- 深层参数名和技术选项；
- JSON、Schema、正则表达式和代码段；
- 协议名、算法名、API 参数名、配置键和枚举值；
- 面向底层实现的专业说明。

负载层可以按阶段处理，但不能把高级区域内的全部内容都自动视为翻译豁免对象。尤其要检查其中是否包含安全、决策、风险或恢复信息。

### 3.3 骨架不等于新手主线

这两个概念的职责不同：

- **骨架**描述界面控件和文本承担的职责；
- **新手主线**描述新手为完成任务经过的路径；
- 新手完成主线时，既会使用骨架，也可能接触少量负载；
- 专家调参时，也必须继续依赖已经本地化的骨架。

因此，不能简单地说“骨架等于新手、负载等于专家”。骨架是全局底线，新手工作量是在骨架基础上，补齐主线中必须理解的负载内容。

## 4. 第三层：工作量由浅到深推进

理解骨架与负载后，就可以通过清晰的阶段规划本地化工作量，而不必一开始逐条检查专家区域。

### L0：骨架全量本地化

优先翻译导航、区域标题、主要操作、任务状态和基础反馈。此阶段建立所有用户都依赖的母语控制层。

### L1：新手主线形成母语闭环

在骨架基础上，补齐新手路径中必须接触的负载：

- 推荐选项的名称和含义；
- 默认值的作用和基本限制；
- 执行前必须理解的条件；
- 结果、失败原因和恢复方式。

此阶段完成后，应做到：

> 新手按照推荐路径操作时，不需要理解专业英文，也不需要查阅外部文档。

### L2：专家区建立清晰边界

翻译专家区的入口、Tab、面板标题和操作动词，但暂时保留深层参数载荷：

```text
高级参数（母语门牌）
  ├─ Temperature: 0.7       （领域原文）
  ├─ Top-P: 0.95            （领域原文）
  └─ [ 恢复默认 ]            （母语操作）
```

### L3：专家区内容渐进补译

当功能趋于稳定、使用频率上升，或用户反馈显示理解困难时，再翻译专家区的重要说明：

- 参数作用；
- 常见组合与建议值；
- 风险、限制与恢复方式；
- 高频功能的帮助说明。

### L4：长期保留必须与实现或规范对齐的技术原文

以下内容通常不必替换为纯母语：

- 官方 API、参数名和配置键；
- JSON、Schema、代码和正则表达式；
- 已形成行业共识且便于检索的术语；
- 必须与实现或官方规范逐字对应的标识符。

工作量的推进顺序因此是：

```text
骨架本地化
→ 新手主线闭环
→ 专家区建立清晰边界
→ 专家区按价值渐进补译
→ 技术标识符长期保真
```

## 5. 两类角色的交互路径

### 新手的母语主线

```text
[进入页面] → [理解页面与推荐选项] → [识别区域门牌] → [执行] → [理解结果]
   母语             母语          母语           母语       母语
```

新手不必进入高级参数区，也不需要理解领域英文。

### 专家的调参路径

```text
[通过母语骨架定位] → [进入高级区域] → [查看领域术语与官方键名]
          ↓
     [调整参数] → [阅读母语操作、风险与反馈] → [保存或执行]
```

专家可以使用英文进行精确调参，同时继续依赖母语导航、操作、警告和恢复信息。

---

## 6. 专家区的翻译顺序

专家区域不需要在第一阶段逐项审查全部文本。进入专家区本地化阶段后，建议按以下顺序处理。

### 6.1 优先豁免行业术语和代码标识符

符合以下条件的内容，可以保留英文或采用双语显示：

- 国际行业通用术语；
- 官方 API 参数名、配置键、协议标识和枚举值；
- 代码、Schema、正则表达式和命令；
- 必须复制、搜索或与官方文档逐字对照的内容。

例如 `Temperature` 可以保留英文，同时提供母语说明：

```text
随机程度（Temperature）
控制输出变化程度。

temperature: 0.7
```

这里，“术语豁免”豁免的是专业标识符本身，而不是与它配套的全部说明文字。

### 6.2 再检查文本属性

在识别出可保留的术语和标识符后，再检查其余人类可读内容：

- **安全**：权限、隐私、数据保护、费用，以及不可逆操作；
- **决策**：用户必须理解后才能选择的选项、范围和限制；
- **风险**：不当配置可能导致失败、不稳定或数据损坏；
- **恢复**：返回、重试、重置、撤销和默认值恢复。

凡涉及以上属性，即使位于专家区，也应优先本地化。

### 6.3 保持三类内容分离

```text
规范标识：       Temperature
人类可读名称：   随机程度（Temperature）
作用与风险说明： 控制输出变化程度；过高可能导致结果不稳定
```

这种结构既保留了专家检索和对照原文的能力，也不需要支持人员或其他读者猜测英文说明的含义。

## 7. 工程落地准则

1. **门牌必须翻译**
   任何具有导航、分区和收纳职责的标题都必须本地化，包括 Tab、折叠面板、抽屉和对话框标题。
2. **区域必须有明确边界**
   暂留英文的内容应集中在独立的高级区域，不应与母语基础设置随机混排。
3. **操作动词必须本地化**
   `应用`、`恢复默认`、`复制配置`、`执行` 等控制动作属于骨架，不应随参数一起留成英文。
4. **漏译与术语保留必须区分**
   计划保留的英文术语应采用一致的标记或双语展示；未计划翻译的文本仍应由自动检查和测试发现，不能借“专家区”概念隐藏漏译。
5. **暂缓不是永久豁免**
   专家区功能稳定、访问频率增加、支持成本上升或进入新手触达范围时，应逐步增加翻译范围。
6. **程序标识符可以保留，但用户说明必须本地化**
   可以直接保留 `temperature` 这样的 API 参数名，以及配置键、枚举值和错误码，因为它们是程序或规范需要引用的固定名称。
   但用于告诉用户“这个参数有什么作用、有哪些风险、应该如何操作”的文字，仍然必须进入消息资源。例如：

   ```text
   temperature                  ← 可保留的程序标识符
   控制输出结果的随机程度         ← 必须本地化的用户说明
   数值过高可能导致结果不稳定      ← 必须本地化的风险提示
   ```

   因此，“保留 `temperature`”只豁免参数名，不豁免 `Controls the randomness of output` 这一整段英文说明；该说明不能直接硬编码在界面中。

---

## 8. 一句话总结

> **先按角色分层，再用骨架确定母语底线；先完成骨架与新手主线，随后在专家区豁免行业术语，最后按安全、决策、风险和恢复属性补齐翻译。**

最终目标不是“所有文字都必须马上翻译”，也不是“高级内容可以长期不翻译”，而是：

> **母语负责理解、控制和决策，专业原文负责精确、检索和规范对齐。**
